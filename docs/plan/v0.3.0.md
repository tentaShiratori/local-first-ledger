## 目的

2 つのブラウザが中継サーバー経由で差分だけを送り合い、同じ状態になる。サーバーはドメインの中身を解釈せず、中継と保管だけを行う（要件 2）。

## 対象範囲

- クライアント間で差分（またはライブラリが定める同期メッセージ）を交換する経路
- 中継サーバーの責務: バイト列の受け取り、保管、再接続時の引き渡し。明細 JSON へのパースや合計計算はしない
- 再接続時に欠けた更新を取得できること
- サーバー再起動後も、保管してある更新からクライアントが追いつけること
- 遅延・重複配送を想定した収束確認（2 レプリカ以上）

## 非対象（このバージョンではやらない）

- フィールド単位の競合 UI、削除方針、予算、重複候補、履歴表示（[v0.4.0](./v0.4.0.md) / [v1.0.0](./v1.0.0.md)）
- P2P 直結、暗号化、一般公開向け認証（発展または対象外）
- クラウドへの本番デプロイ、課金、常時公開（実施しない）

## 設計の理由

1. 要件 2 は「サーバーが家計簿を理解する」ことではなく、オフライン編集の結果を運ぶこと。解釈しない中継にすると、学習対象が CRDT 側に残る
2. 差分同期は v0.1.0 の「状態全体交換」より実運用に近い。v0.1.0 で学んだ収束前提のうえに載せる
3. 通信方式を最初から確定済みと書かない。学習用には信頼できる限定ネットワークで 2 端末検証する

## 推奨案（仮置き・未確定）

| 項目 | 推奨案（仮） | 注意 |
| --- | --- | --- |
| 通信 | WebSocket 双方向を候補とする | HTTP ポーリング等でもよい。当たり前の確定扱いにはしない |
| サーバー保管 | ドキュメント ID ごとに opaque な更新バイト列を追記保存 | 中身を家計簿として読まない |
| 再接続 | クライアントが持つバージョン情報（ライブラリの sync / version vector 相当）に基づき不足分だけ取得 | 方式は選定ライブラリに合わせる |
| 公開範囲 | 自分の 2 端末、または閉じた検証環境 | 認証なし一般公開は勧めない |

## サーバー責務の具体化

| してよいこと | してはいけないこと |
| --- | --- |
| 接続の受け付けと切断の検知 | 明細フィールドの検証や書き換え |
| 更新バイト列の保存と返却 | 合計・残高・カテゴリの計算 |
| 再接続クライアントへの不足分配送 | 「正しい家計簿状態」への裁定 |

保持・再接続取得・サーバー再起動後の復元は、受け入れ条件と検証に含める。

## 受け入れ条件（v0.3.0 機能完了時）

1. 2 ブラウザがオンラインなら、一方の入力が他方に届き、最終状態が一致する
2. 交換しているのは差分（またはライブラリ同期メッセージ）であり、サーバーはドメイン解釈をしない
3. 一時切断のあと再接続すると、欠けていた更新を取り込める
4. サーバープロセスを再起動しても、保管分からクライアントが同じ状態へ戻れる
5. 同じ更新を重複して受け取っても状態が壊れない（v0.3.0 の同期経路上で確認）

## 実行予定の検証

| 検証 | 内容 |
| --- | --- |
| 2 ブラウザ同期 | 片方で明細追加 → 他方が同じ一覧になる |
| 分断後再同期 | オフラインで双方入力 → オンライン復帰後に一致 |
| 重複配送 | 同じ更新を 2 回流しても読取値が変わらない |
| 遅延 | 古い更新を後から届けても最終一致 |
| サーバー再起動 | 保管データから再接続クライアントが復元 |
| 環境スモーク | 収束の証拠に使わない |

## 残る選択

- WebSocket 以外の輸送手段
- サーバーの保存媒体（メモリのみは再起動検証に不十分。ファイルまたは埋め込み DB などを後で選ぶ）
- 複数ドキュメント（家計簿が複数ある場合）の ID 設計
