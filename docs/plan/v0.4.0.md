## 目的

同時編集が日常的に起きる前提で、次を実装する。

- 要件 3: 同じ明細の別項目の同時修正は両方残し、同一項目は一方に決まる。決まり方を説明できる
- 要件 4: 削除と編集がぶつかったときの方針を決めて実装する
- 要件 5: 合計・残高は明細から計算する。カテゴリ予算は上書きではなく足し引きとし、同時変更を両方反映する
- 要件 6: マージは成功したが困るケース（同一レシートの二重入力など）を重複候補として表示する。自動削除しない

## 対象範囲

- 明細をフィールド単位で更新できるデータモデル（Map 相当）
- 同一フィールド競合の決定的解決と、説明用の短い文書（壁時計と混同しない）
- 削除と編集の衝突方針の確定と実装
- 派生合計の計算（永続化しない）
- カテゴリ予算のカウンタ型更新
- 重複候補の検出と表示（ユーザーが判断。自動では消さない）

## 非対象（このバージョンではやらない）

- 明細ごとの変更履歴 UI（[v1.0.0](./v1.0.0.md)）
- 2 ブラウザ×各 5 件の最終統合シナリオ全体（v1.0.0。ただし v0.4.0 の部品はそこで再利用する）
- 銀行 CSV、undo、暗号化（発展。必須に足さない）

## 設計の理由

1. CRDT が自動でそろえる衝突と、そろっても意味的に困る衝突を分けると、要件 3 と 6 の学びが混ざらない
2. 合計を保存しないことで、レプリカ間で合計だけがずれるクラスの不具合を避ける
3. 予算を LWW 数値にすると同時増減が欠ける。カウンタ型（または同等）が要件 5 の文言に合う

## ドメインの不変条件（計画）

- 明細 ID は作成時に決まり、マージで勝手に融合しない（別 ID なら別明細）
- 表示上の合計は削除されていない明細の金額から都度計算する
- 予算の現在値は足し引き操作の累積結果であり、最後の上書き 1 回ではない
- 重複候補は提案であり、候補表示だけで明細を消さない

## 推奨方針（仮置き・未確定）

### 同一フィールドの勝者（要件 3）

推奨案（Automerge 公式 Conflicts に沿う説明用）: 勝者は操作 ID（論理カウンタと actorId）に基づく。壁時計の「実時間の最後」ではない。別フィールドなら両方残る。

Yjs / Loro を選んだ場合は、その公式仕様の勝者規則を同じ場所に書き換える。実装前に「説明できる」文を計画へ残す。

### 削除と編集（要件 4）

編集優先か削除優先かは **未決のまま** でよい。同じキーへの delete と set の規則だけを、明細削除と子フィールド編集の結果保証に使わない。

#### 操作の区別（別トポロジー）

家計簿で扱う衝突は少なくとも次を分けて書く。

| 層 | 例 | 備考 |
| --- | --- | --- |
| 明細マップのエントリ | 親 Map のキー（明細 ID）の有無 | 「明細全体を消す」操作の置き場 |
| 子フィールド | その明細の `date` / `amount` / `category` / `memo` など | 要件 3 のフィールド単位更新 |
| 削除の表現 | キー削除、墓石、`deleted` フラグなど | どれを採用するかは未決 |

「親 Map で明細エントリを消す」と「残っている明細の子フィールドを直す」は、同じキーへの delete と set とは別操作・別トポロジーである。公式の「同じキーへの delete と set なら set が残る」類の規則を、この衝突へそのまま当てはめる推論はしない。

明細全体を 1 回の set で置き換えて編集優先を無理に作ると、別フィールドの並行変更保持（要件 3）を壊す恐れがある。そのやり方を推奨しない。

#### 着手前の確認（実装・プロトタイプはまだしない）

v0.4.0 の削除×編集に着手する前に、次の順で止めて確定する。

1. 明細マップ / 子フィールド / 削除表現の具体形を文書に固定する
2. 選定ライブラリの公式仕様で、その形における既定動作を確認する
3. 将来の固定例テストで、配送順を入れ替えても同じ既定結果になることを観測する
4. 観測結果を踏まえ、アプリ方針（編集優先・削除優先・その他）と受け入れ期待値を合意してから実装する

同じキーへの set 競合の規則だけでは、明細削除と子フィールド編集がぶつかったときの結果を保証しない。

### 予算（要件 5）

推奨案: ライブラリの Counter（Automerge.Counter / LoroCounter 等）。Yjs の場合は専用 Counter が公式に無い前提で、同等の足し引き CRDT を設計してから着手する。増分だけでなく減分も必須条件に含める。

### 重複候補（要件 6）

推奨案: 金額・日付・（あれば）メモ類似など、アプリが定義するヒューリスティックで候補を並べる。CRDT マージ成功後も一覧に残す。ユーザーが「別物」「片方を削除」などを選ぶまで自動削除しない。

## 受け入れ条件（v0.4.0 機能完了時）

1. 同じ明細の別フィールドを 2 レプリカが同時に直すと、同期後に両方の変更が残る
2. 同じフィールドを同時に直すと、決めた規則どおり一方に決まり、その決まり方を短文で説明できる
3. 削除と編集の衝突について、上記の着手前確認で合意した方針と受け入れ期待値どおりの結果になる
4. 合計は保存データではなく計算結果である
5. 予算の並行する増加と減少が両方とも反映される（上書きで片方だけが残る結果にならない）
6. 二重入力に相当するケースで重複候補が出る。候補表示だけでは明細が消えない

## 実行予定の検証

| 検証 | 内容 |
| --- | --- |
| 固定例（別フィールド） | A が memo、B が amount を同時変更 → 両方残る |
| 固定例（同一フィールド） | 両方 amount → 方針どおりの一方 |
| 削除×編集 | 着手前確認のあと固定した期待値で、順序入れ替えも含めて一致 |
| 予算並行（増分のみ） | 初期 0 で同時 +100 と +50 → 最終 +150 |
| 予算並行（増減） | 初期 0 で同時 +100 と -30 → 最終 +70 |
| 予算の順序・重複 | 上の予算例を配送順変更および重複配送しても最終値が不変 |
| 重複候補 | 似た 2 明細が候補になり、自動削除されない |
| 順序変更・重複配送 | フィールド競合・削除編集のシナリオでも最終一致 |
| 環境スモーク | 使わない（証拠にしない） |

## 残る選択

- 編集優先か削除優先か（未決。着手前確認のあと合意する）
- 明細マップ / 子フィールド / 削除表現の具体形
- 重複判定の具体閾値（完全一致のみか、近傍か）
- 競合の敗者を UI に出すか（Automerge `getConflicts` 相当を学習表示に使うか）
