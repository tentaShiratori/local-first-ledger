## 目的

1. 明細ごとに「誰がいつ何を変えたか」の履歴を表示する（要件 8）
2. 要件ページの統合完了条件を、観測可能な形で通す
3. 人が行う 1 週間の実用確認を、期間の最後に確保する

## 対象範囲

- 明細単位の変更履歴表示（誰 / いつ / 何が変わったか）
- 因果順と壁時計（実時間）の違いを UI または短い説明で区別できること
- 統合シナリオ: 2 ブラウザ×各 5 件入力＋同じ明細の並行編集→オンライン復帰後の一覧と合計の一致
- 3 端末の同期順入れ替え、重複配送、削除と編集、自作 CRDT ランダム一致の再確認（自動テスト）
- 人手 1 週間の受け入れ手順書（実データ投入・家族連絡は人が行う。エージェントは実施しない）

## 非対象（このバージョンではやらない）

- 発展要件（P2P、暗号化、長期肥大測定、銀行 CSV、undo）の必須化
- 本番一般公開、課金、認証基盤
- エージェントによる実家族データの操作

## 設計の理由

1. 履歴は「今の値」だけでなく学習の仕上げになる。因果順と実時間を混同すると、要件 3 の LWW 説明とも矛盾する
2. 統合シナリオは部品テストの合計では足りない。配送後の内部状態と画面上の一覧・合計を同じ観測で見る
3. 1 週間の実用は自動テストでは代替できない。計画上は人が行う受け入れとして残す

## 履歴（要件 8）の扱い

| 項目 | 方針 |
| --- | --- |
| 誰 | 入力者または端末／actor の識別子（本格アカウントではない） |
| いつ | 可能なら壁時計の記録と、因果・操作順を分けて示す。片方しか取れない場合は「実時間ではない」旨を明示する |
| 何 | どのフィールドがどう変わったか（少なくとも前後が追える） |
| 推奨案（仮） | 選定ライブラリの履歴 API（Automerge の変更履歴、Loro の checkout／履歴など）。Yjs の場合はアプリ側で変更ログを載せる設計が必要になりやすい |

## 統合検証で必ず含めること

次を v1.0.0 で必ず実施する。ビルド成功や環境スモーク成功は収束の証拠にしない。

1. 2 つのブラウザをオフラインにする
2. それぞれ 5 件入力する
3. 同じ明細を両方で編集する
4. オンラインに戻す
5. 一覧と合計が完全に一致することを、画面（または同等の観測手段）と内部状態の両方で確認する

あわせて要件ページの次も自動テストで再確認する。

- 3 つの端末の同期順を入れ替えても最終状態が一致する
- 同じ変更を 2 回受け取っても状態が変わらない
- 削除と編集がぶつかったとき、決めた方針どおりになる
- 自作カウンタと後勝ちレジスタが、ランダム順でも一致する（v0.1.0 のテストが緑のまま）

## 人手 1 週間の実用確認（人が行う）

| 項目 | 内容 |
| --- | --- |
| 目的 | 自分の 2 台、または家族と 1 週間実際に使う |
| 実施者 | リポジトリ利用者（人） |
| エージェントがしないこと | 実データ投入、家族への連絡、実運用の開始・監視 |
| 計画上の置き場 | 4 週目の後半。統合自動検証のあとに確保する |
| 記録 | 困ったこと（重複、削除競合、オフライン起動、同期遅れ）を短く残す |

仮の工数目安（保証ではない）: 統合の仕上げと手順整備に数時間、1 週間の実用はカレンダー上の経過が本体。週 8〜10 時間の目安内に収まらない場合は、必須を削らず「カレンダー上の 1 週間が律速」とリスクに書く。

## 受け入れ条件（v1.0.0＝ざっくり完成）

1. 明細ごとに履歴（誰 / いつ / 何）を表示できる。因果と実時間の違いが説明できる
2. 上記の 2 ブラウザ統合シナリオで、一覧と合計が一致する
3. 3 端末順入れ替え・重複配送・削除編集方針・自作 CRDT ランダムの自動テストが通る
4. 人手 1 週間の実用確認が完了した記録がある（人が記入）
5. 発展要件未着手でも、完成定義上は完成としてよい

## 実行予定の検証

| 検証 | 内容 |
| --- | --- |
| 履歴表示 | 同時編集後に、各変更の主体と内容が追える |
| 統合シナリオ | 2×5＋同一明細並行編集。内部と表示の一致 |
| 回帰 | v0.1.0〜v0.4.0 の受け入れテスト |
| 人手 1 週間 | チェックリストに沿った利用記録 |
| 環境スモーク | 引き続き環境専用。完成の証拠にしない |
