## 目的

1. 明細ごとに「誰がいつ何を変えたか」の履歴を表示する（要件 8）
2. 要件ページの統合完了条件を、観測可能な形で通す
3. 人が行う 1 週間の実用確認を、期間の最後に確保する

## 対象範囲

- 明細単位の変更履歴表示（誰 / いつ / 何が変わったか）
- 因果順と壁時計（実時間）の違いを UI または短い説明で区別できること
- 統合シナリオ: 2 ブラウザ×各 5 件入力＋同じ明細の並行編集→オンライン復帰後の一覧と合計の一致
- 3 端末の同期順入れ替え、重複配送、削除と編集、自作 CRDT ランダム一致の再確認（自動テスト）
- 人手 1 週間の受け入れ手順書（実データ投入・家族連絡は人が行う。エージェントは実施しない）

## 非対象（このバージョンではやらない）

- 発展要件（P2P、暗号化、長期肥大測定、銀行 CSV、undo）の必須化
- 本番一般公開、課金、認証基盤
- エージェントによる実家族データの操作

## 設計の理由

1. 履歴は「今の値」だけでなく学習の仕上げになる。因果順と実時間を混同すると、要件 3 の LWW 説明とも矛盾する
2. 統合シナリオは部品テストの合計では足りない。配送後の内部状態と画面上の一覧・合計を同じ観測で見る
3. 1 週間の実用は自動テストでは代替できない。計画上は人が行う受け入れとして残す

## 履歴（要件 8）の実装方針

Yjs にはアプリ向けの変更履歴 API がない。Automerge / Loro の履歴機能も使わない（本リポジトリは Yjs 固定）。そのためアプリ側で追記専用ログを載せる。

| 項目 | 方針 |
| --- | --- |
| 格納 | `Y.Map("entryHistory")` に不変イベントを載せる（G-Set 相当） |
| キー | `${deviceId}:${deviceSeq}:${uuid}`。並行追加はすべて残り、同一更新の再適用は Yjs の冪等性で吸収 |
| 誰 | `enteredBy`（表示名）と `deviceId`（端末） |
| いつ（壁時計） | `wallClockMs`。記録端末の `Date.now`。同期順や正しさの根拠にしない |
| いつ（操作順） | `deviceSeq`。端末ローカルの単調カウンタ（localStorage またはメモリ）。同一端末内の並び替えに使う |
| 何 | `changes[]` にフィールドの前→後 |
| UI | 明細の「履歴」ボタン → タイムライン。並べ替えを「操作順 / 壁時計」で切替。説明文で両者を区別 |
| 壊さないもの | v0.4.0 のネスト Map・編集優先墓石・PN-Counter 予算・重複候補 |

端末間の真の因果（ベクトル時計）は持たない。操作順は「端末ごとの操作順＋決定的タイブレーク」であり、壁時計とは別物だと UI に書く。

## 統合検証で必ず含めること

次を v1.0.0 で必ず実施する（後続 PR）。ビルド成功や環境スモーク成功は収束の証拠にしない。

1. 2 つのブラウザをオフラインにする
2. それぞれ 5 件入力する
3. 同じ明細を両方で編集する
4. オンラインに戻す
5. 一覧と合計が完全に一致することを、画面（または同等の観測手段）と内部状態の両方で確認する

あわせて要件ページの次も自動テストで再確認する。

- 3 つの端末の同期順を入れ替えても最終状態が一致する
- 同じ変更を 2 回受け取っても状態が変わらない
- 削除と編集がぶつかったとき、決めた方針どおりになる
- 自作カウンタと後勝ちレジスタが、ランダム順でも一致する（v0.1.0 のテストが緑のまま）

## リスク（正直な見積）

- オフライン起動（キャッシュ）は環境差が出やすい
- 削除方針の変更は v0.4.0 テストの作り直しになる
- 1 ヶ月カレンダーと 30〜40 時間は目安。必須を削らず、遅れる場合はバージョンの完了日をずらす
- 端末時計のずれで壁時計順が直感と違うことがある（仕様どおり）
