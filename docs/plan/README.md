## 完成の定義（このリポジトリでの「ざっくり完成」）

次をすべて満たしたときを v1.0.0 完了＝ざっくり完成とする。

| 区分 | 内容 |
| --- | --- |
| 必須要件 | 要件 1〜8 |
| 統合検証 | 2 ブラウザをオフラインにして各 5 件入力し、同じ明細を両方で編集してからオンラインに戻すと一覧と合計が一致する。3 端末の同期順入れ替え一致、重複配送で不変、削除と編集の方針どおり、自作 CRDT のランダム一致 |
| 人手実用 | 自分の 2 台または家族と 1 週間実際に使う（人が行う受け入れ。エージェントは実データ投入・家族連絡・実運用開始をしない） |

発展要件（P2P、暗号化、長期肥大測定、銀行 CSV、undo）は完成条件に含めない。4 週目に必ず追加する約束もしない。

期間・工数（1 ヶ月、合計 30〜40 時間、週 8〜10 時間）は要件ページの目安であり、実測や保証ではない。必須を削らず進める。1 ヶ月で厳しい場合はリスクとして残し、必須項目は条件付き見積で示す。

## 週次対応（目安）

| 週 | バージョン | 内容 |
| --- | --- | --- |
| 1 | v0.1.0 | 要件 7 |
| 2 | v0.2.0 → v0.3.0 | 要件 1、2 |
| 3 | v0.4.0 | 要件 3、4、5、6 |
| 4 | v1.0.0 | 先に要件 8（履歴）と必須の統合検証。それが終わってから人手 1 週間の実用を開始する |

4 週目に履歴開発・統合テスト・丸 1 週間の実用を同時に置くと、カレンダー上の 1 ヶ月を超えうる。人手 1 週間の開始前に、履歴と必須統合を終える必要がある。準備が遅れた場合は、実用の 1 週間を短縮せず、完成日を延ばす。期間・工数の数字自体は目安のままとする。

未検証のバージョンの上に次を重ねて「できた」扱いにしない。各バージョンの受け入れを満たしてから次へ進む。

## ライブラリ選定（採用済み: Yjs）

**採用は Yjs。** 索引作成時の推奨は Automerge だったが、v0.2.0 実装で人気を理由に Yjs へ確定した（Automerge 推奨は上書き）。

測定日 2026-11-10（対象週 2026-11-03〜2026-11-09、ライブ API）:

| 指標 | Yjs | Loro | Automerge |
| --- | --- | --- | --- |
| npm 週間 DL | yjs 15,689,133 | loro-crdt 215,369 | @automerge/automerge 120,380 / automerge 11,418 |
| GitHub stars | yjs/yjs 23,042 | loro-dev/loro 6,283 | automerge/automerge 6,723 |

公式ドキュメントの出典は次のとおり。

- Automerge: [Welcome](https://automerge.org/docs/hello/)、[Conflicts](https://automerge.org/docs/reference/documents/conflicts/)、[Counters](https://automerge.org/docs/reference/documents/counters/)、[Merge rules](https://automerge.org/docs/reference/under-the-hood/merge-rules/)、[Concepts](https://automerge.org/docs/reference/concepts/)
- Yjs: [Docs](https://docs.yjs.dev/)、[Y.Map](https://docs.yjs.dev/api/shared-types/y.map)、[Offline / IndexedDB](https://docs.yjs.dev/getting-started/allowing-offline-editing)
- Loro: [loro.dev](https://loro.dev)、[Getting started](https://loro.dev/docs/tutorial/get_started)、[Sync](https://loro.dev/docs/tutorial/sync)、[Persistence](https://loro.dev/docs/tutorial/persistence)

| 観点 | Automerge | Yjs（採用） | Loro |
| --- | --- | --- | --- |
| Map（別フィールド同時編集） | 別プロパティは両方残る（公式 Conflicts） | `Y.Map` でキー単位にマージ | `LoroMap`。JSON 互換の Map |
| 同一フィールド競合 | 読み取りは LWW。勝者は操作 ID（カウンタ＋actorId）。**壁時計ではない**。敗者は `getConflicts` で残る | 共有型として決定的に収束。壁時計 LWW とは限らない | Map の同一キーは競合規則で一方が見える状態になり得る（公式 Sync の注意） |
| 削除 | 削除と同時 set では set 側が残る、と Merge rules に明記 | `delete` あり。削除と更新の意味方針はアプリで決める必要あり | delete あり。意味方針はアプリで決める必要あり |
| 増減カウンタ | `Automerge.Counter` が公式型 | コアに専用 Counter 型は見当たらない。数値の素朴な上書きは要件 5 に不向き | `LoroCounter` が公式型 |
| 永続化 | ドキュメント履歴を含むバイナリ。`automerge-repo` が保管・同期の枠 | `y-indexeddb` など provider で更新を永続化 | `export` / `import`（snapshot / update）。保管はアプリ側 |
| 差分同期 | ネットワーク非依存。同期プロトコルあり。中継は中身を解釈しなくてよい | ネットワーク非依存。provider が配送。中継は中身を解釈しなくてよい | update の export/import。配送手段はアプリ側 |
| 履歴（誰がいつ何を） | 変更履歴を文書が保持。履歴閲覧・比較が設計原則に含まれる | スナップショットや Undo はあるが、明細単位の「誰がいつ何を」はアプリ設計の比重が大きい | checkout / 履歴が公式に強い |

### 旧推奨（記録）と後続負債

Automerge を推奨していた理由（記録）:

1. 要件 3 の「別項目は両方・同一項目は一方」と、公式の Map 競合説明が対応しやすい
2. 要件 5 の予算足し引きに `Counter` がそのまま使える
3. 要件 8 の変更履歴を、文書が持つ履歴として扱いやすい

Yjs 採用により、**要件 5 の Counter 相当**と**要件 8 の履歴**は後続バージョンの受け入れ前に設計を書き直す（実装はそれぞれのバージョンで行う。[v0.2.0](./v0.2.0.md) でも明記）。

## 学習用ネットワークの前提

同期の検証は信頼できる限定ネットワーク（自分の 2 端末、または閉じた検証環境）で行う想定とする。認証なしの一般公開は勧めない。デプロイや課金は計画の実施対象外（このリポジトリ作業では行わない）。
