## 目的

端末ごとの CRDT ドキュメントに明細（日付、金額、カテゴリ、メモ、入力者）を持ち、ブラウザ内に保存する。電波がなくてもアプリを起動し、入力と閲覧ができる（要件 1）。

再読込での復元と、起動そのものをネットワークなしで行えることを分けて扱う。

## 対象範囲

- CRDT ライブラリの選定確定（比較は索引を正とする）
- 明細を保持するドキュメント形状の最小定義
- ブラウザ内永続化（推奨案: IndexedDB 系。確定ではない）
- オフラインでのアプリ起動（静的アセットのローカル提供。起動キャッシュ手段は未決なら推奨案として Service Worker / アプリキャッシュ相当を仮置き）
- 一意な端末（レプリカ）ID の発行と保存
- 同一プロファイル複数タブの扱い方針の決定と、少なくとも危険を示す検証

## 非対象（このバージョンではやらない）

- 中継サーバーと端末間の差分同期（[v0.3.0](./v0.3.0.md)）
- フィールド競合・削除方針・予算カウンタ・重複候補・履歴 UI（後続）
- 認証、グラフ、銀行 API、ネイティブアプリ（プロジェクト全体の対象外）

## 設計の理由

1. 要件 1 は「つながったら同期」より先に、端末が単独で生きることを求める。同期未接続でも起動・入力・保存ができなければローカルファーストにならない
2. ライブラリ選定を永続化と同じバージョンに置くのは、保存形式がライブラリのバイナリ／更新列に依存するため。選定前に独自保存を固めると作り直しになる
3. 端末 ID と複数タブは後続の後勝ち・履歴・同期の前提になる。後から変えるとテストが崩れる

## データ形状（計画上の最小）

明細は少なくとも次を持つ。保存の正規形は CRDT ドキュメント側とし、合計・残高は持たない（要件 5。計算は後続でも可だが、永続化対象に合計を入れない）。

- `id`（作成時に端末が発行する一意 ID）
- `date` / `amount` / `category` / `memo` / `enteredBy`
- 削除フラグまたは削除相当の表現は、削除方針を決める [v0.4.0](./v0.4.0.md) まで仮でよい。ただし v0.2.0 で「消したつもりが再読込で戻る」ことがないよう、採用した削除表現があれば永続化対象に含める

入力者は本格アカウントではなく、家族の名前を選ぶ程度でよい（対象外の認証と混同しない）。

## 受け入れ条件（v0.2.0 機能完了時）

1. ライブラリが文書上で選定済み（推奨からの変更があれば理由を残す）
2. ネットワークを切った状態でアプリを起動できる
3. オフラインで明細を追加・閲覧できる
4. ブラウザを終了して開き直しても、同じ端末の明細が復元される
5. 端末 ID が再起動後も安定して同じである
6. 同一プロファイル複数タブについて、決めた方針どおりの挙動または明示警告がある

## 実行予定の検証

| 検証 | 内容 |
| --- | --- |
| オフライン起動 | DevTools などでネットワーク遮断し、アプリ本体が起動して入力画面に達する |
| 保存再読込 | 明細を入れてリロード／再起動し、同一内容が戻る |
| 端末 ID 安定 | 再起動前後で ID が変わらない |
| 複数タブ | 決めた方針に沿う固定例（同時入力の危険または排他） |
| 環境スモーク | 既存のまま。収束や同期の証拠にしない |

## 残る選択

- Automerge 以外を選ぶ場合の Counter / 履歴の代替設計
- Service Worker の要否（開発用ローカル配信だけで週次学習を進めるか）
- 複数タブの排他方式の具体実装
