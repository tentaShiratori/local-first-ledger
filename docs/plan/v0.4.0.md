## 目的

同時編集が日常的に起きる前提で、次を実装する。

- 要件 3: 同じ明細の別項目の同時修正は両方残し、同一項目は一方に決まる。決まり方を説明できる
- 要件 4: 削除と編集がぶつかったときの方針を決めて実装する
- 要件 5: 合計・残高は明細から計算する。カテゴリ予算は上書きではなく足し引きとし、同時変更を両方反映する
- 要件 6: マージは成功したが困るケース（同一レシートの二重入力など）を重複候補として表示する。自動削除しない

## 対象範囲

- 明細をフィールド単位で更新できるデータモデル（Map 相当）
- 同一フィールド競合の決定的解決と、説明用の短い文書（壁時計と混同しない）
- 削除と編集の衝突方針の確定と実装
- 派生合計の計算（永続化しない）
- カテゴリ予算のカウンタ型更新
- 重複候補の検出と表示（ユーザーが判断。自動では消さない）

## 非対象（このバージョンではやらない）

- 明細ごとの変更履歴 UI（[v1.0.0](./v1.0.0.md)）
- 2 ブラウザ×各 5 件の最終統合シナリオ全体（v1.0.0。ただし v0.4.0 の部品はそこで再利用する）
- 銀行 CSV、undo、暗号化（発展。必須に足さない）

## 設計の理由

1. CRDT が自動でそろえる衝突と、そろっても意味的に困る衝突を分けると、要件 3 と 6 の学びが混ざらない
2. 合計を保存しないことで、レプリカ間で合計だけがずれるクラスの不具合を避ける
3. 予算を LWW 数値にすると同時増減が欠ける。カウンタ型（または同等）が要件 5 の文言に合う

## ドメインの不変条件（計画）

- 明細 ID は作成時に決まり、マージで勝手に融合しない（別 ID なら別明細）
- 表示上の合計は削除されていない明細の金額から都度計算する
- 予算の現在値は足し引き操作の累積結果であり、最後の上書き 1 回ではない
- 重複候補は提案であり、候補表示だけで明細を消さない

## 推奨方針（仮置き・未確定）

### 同一フィールドの勝者（要件 3）

推奨案（Automerge 公式 Conflicts に沿う説明用）: 勝者は操作 ID（論理カウンタと actorId）に基づく。壁時計の「実時間の最後」ではない。別フィールドなら両方残る。

Yjs / Loro を選んだ場合は、その公式仕様の勝者規則を同じ場所に書き換える。実装前に「説明できる」文を計画へ残す。

### 削除と編集（要件 4）

推奨案（仮）: Automerge の Merge rules にある「一方が削除し、他方が同じキーへ set したなら set 側が残る」を初期方針とする。学習用に説明しやすく、公式に文書化されているため。

代替案（選ぶなら v0.4.0 内で確定）: 削除を優先する。その場合はライブラリ既定とずれるため、アプリ層の墓石／削除スタンプで明示する。

**実装着手前にどちらかへ確定し、受け入れテストをその方針に固定する。**

### 予算（要件 5）

推奨案: ライブラリの Counter（Automerge.Counter / LoroCounter 等）。Yjs の場合は専用 Counter が公式に無い前提で、同等の足し引き CRDT を設計してから着手する。

### 重複候補（要件 6）

推奨案: 金額・日付・（あれば）メモ類似など、アプリが定義するヒューリスティックで候補を並べる。CRDT マージ成功後も一覧に残す。ユーザーが「別物」「片方を削除」などを選ぶまで自動削除しない。

## 受け入れ条件（v0.4.0 機能完了時）

1. 同じ明細の別フィールドを 2 レプリカが同時に直すと、同期後に両方の変更が残る
2. 同じフィールドを同時に直すと、決めた規則どおり一方に決まり、その決まり方を短文で説明できる
3. 削除と編集の衝突結果が、文書化した方針とテストの期待値どおりである
4. 合計は保存データではなく計算結果である
5. 予算を 2 者が同時に足し引きすると、両方の差分が反映される
6. 二重入力に相当するケースで重複候補が出る。候補表示だけでは明細が消えない

## 実行予定の検証

| 検証 | 内容 |
| --- | --- |
| 固定例（別フィールド） | A が memo、B が amount を同時変更 → 両方残る |
| 固定例（同一フィールド） | 両方 amount → 方針どおりの一方 |
| 削除×編集 | 方針確定後の期待値で順序入れ替えも含めて一致 |
| 予算並行 | 同時 +100 と +50 → 最終 +150（初期 0 の例） |
| 重複候補 | 似た 2 明細が候補になり、自動削除されない |
| 順序変更・重複配送 | 上記シナリオを配送順入れ替え／重複でも最終一致 |
| 環境スモーク | 使わない（証拠にしない） |

## 残る選択

- 削除優先か編集（set）優先か
- 重複判定の具体閾値（完全一致のみか、近傍か）
- 競合の敗者を UI に出すか（Automerge `getConflicts` 相当を学習表示に使うか）
